# RAG Workbench v0.4.0 (draft)

Draft: updated as work lands. Items under "Still to do before release" are not in yet.

## New

- **Optional reranker.** A small reranker model can reorder the best 20 candidates before the
  cut, which is the largest accuracy gain available after retrieval itself.
  - Off by default. Turn it on with `rag search --rerank`, with `[rerank] enabled = true` in a
    workspace's `config.toml`, or with the switch in the app's Search tab.
  - It needs a `/v1/rerank` endpoint over plain http, for example
    `llama-server -m Qwen3-Reranker-0.6B-Q8_0.gguf --reranking --port 8081`. The address is
    `--rerank-url`, `RAG_RERANK_URL`, or the field beside the switch.
  - If the reranker can't be reached, the search still answers in the usual order and says it
    wasn't reranked.
- **One search implementation everywhere.** Everything after the query embedding (vector and
  keyword search, rank fusion, duplicate removal, reranking, neighbour expansion, citations, the
  agent's Markdown form) now runs in one shared engine. The Workbench calls it from Python and the
  retrieval server from C# (`ShammyRetriever`), so the agent gets exactly what the Search tab
  shows, for sqlite-vec and Shammy knowledge bases alike.

- **Shammy, the project's own vector store.** A workspace can keep its vectors in a single
  `vectors.shammy` file instead of inside `rag.db`.
  - About 12.8 KB per chunk at 4096 dimensions, against 16.4 KB in sqlite-vec.
  - A search scans a 1-bit sketch of every chunk, reranks on 1-bit and 8-bit codes, then rescores
    the best 50 exactly. On 50,000 chunks at 4096 dimensions that takes 1 to 2 ms on one thread.
  - Uses AVX2 or AVX-512 when the CPU has them and as many threads as you allow (default: two
    fewer than the machine's cores). Results are identical on every CPU and thread count.
  - Every section of the file has a checksum, and an interrupted write never damages what was
    already saved.
- **`rag init WS --vectors shammy`** starts a workspace on Shammy.
- **`rag convert WS`** moves an existing workspace's vectors to Shammy, and
  `rag convert WS --to sqlite-vec` moves them back. Nothing is embedded again.
- **In the desktop app:** New knowledge base offers the vector store, and the About tab shows which
  one a knowledge base uses, with a button to move the vectors to Shammy or back.
- **`rag compact WS`** rewrites `vectors.shammy` without deleted rows. Builds do it on their own
  when a quarter of the rows are deleted.
- **Import from other databases.** `shammy-convert sqlite` reads sqlite-vec tables and ordinary
  SQLite tables; `shammy-convert pgvector` reads a PostgreSQL pgvector column. Models whose
  vectors aren't a power of two in size (768, 1536, ...) are stored padded.
- **A Python module, `shammy`**, for using the store outside RAG Workbench: create, add, delete,
  search with filters, read vectors back, verify, compact.
- **A C interface and a C# wrapper** for reading Shammy files from other programs, including the
  .NET retrieval server. `shammy/dotnet/README.md` shows the change the server needs to read
  `ragpack/2` packs. The native library (`shammy.dll`, `libshammy.so`) and `shammy.h` are attached
  to the release as `shammy-native-<OS>.zip`. C, C# and Python return identical results.
- **`rag export --slim`** (Shammy workspaces) leaves the float16 vector copies out of the pack:
  about 4.6 KB of vectors per chunk at 4096 dimensions instead of 12.8 KB. Results from a slim
  pack are ranked by the 8-bit codes without the exact rescore, and a slim pack can't be merged
  into another knowledge base.

## Changed

- Build, search, merge, verify, status, export and unpack work the same on both stores.
  `rag merge` copies between a sqlite-vec workspace and a Shammy one.
- `rag search` and the app's Search tab use the shared engine. Results are the same as before;
  the earlier Python implementation is kept as a reference that a test compares against, and it
  is what runs (without reranking) if the engine module isn't installed.
- `rag verify` on a Shammy workspace also checks every checksum in `vectors.shammy` and that
  every chunk has a vector.
- `rag status` and `rag verify` show which store a workspace uses.
- After a crash mid-build on Shammy, the next build drops vectors that have no chunk and reads
  again any document whose vectors didn't reach the disk.

## Compatibility

- sqlite-vec stays the default, and existing workspaces and `ragpack/1` packs are unchanged.
- A pack exported from a Shammy workspace is format **`ragpack/2`**. This version reads both
  formats. The Windows retrieval server reads only `ragpack/1` until it is updated with the C#
  wrapper (see `shammy/dotnet/README.md`); until then keep workspaces that feed it on sqlite-vec.
- Shammy needs a vector size that is a power of two (1024, 2048, 4096). Other sizes are refused
  at `rag init` and `rag convert`.
- Moving from Shammy back to sqlite-vec writes Shammy's float16 copies of the vectors, which
  differ from the originals only past the fourth significant digit.

## Still to do before release

- Windows: the writer lock, file replacement during compaction and the installer build with the
  bundled `shammy` module have only run on Linux so far.
- Desktop app: the new store choice and the move button are type-checked and covered by engine
  tests, but haven't been looked at in a running window yet.
- Retrieval server: switch the .NET MCP server's search to `ShammyRetriever`
  (`shammy/dotnet/README.md`) and try both pack formats against it. The wrapper is tested on Linux only.
- Reranker: tested against a stand-in `/v1/rerank` server, not yet against a real reranker model.
  The app doesn't start or download a reranker; you run it yourself for now.
- A default for how many candidates stage 1 keeps, measured on a large real knowledge base.
