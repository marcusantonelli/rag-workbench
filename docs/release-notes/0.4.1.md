# RAG Workbench v0.4.1

Procedures come back as procedures, the agent can read on through long ones, builds show what
they are doing, and the app updates itself from now on. Knowledge bases built with 0.4.0 keep
working unchanged and get the new structure in seconds, without reading or embedding anything
again.

**Install this version by hand once** (the updater arrives with it); later versions are offered
inside the app.

## Procedures

- **The spots file.** Every build writes `structure.spots` next to `rag.db`. It records which
  chunks make up each procedure and its steps, the warnings and notes inside each step, the
  references between steps and documents ("see Section 8.4", "see FX-100"), and each document's
  number and revision (from its title block or file name).
  - Three shapes of procedure are recognised: numbered headings (7.0 → 7.1, 7.2 …, with sub-steps
    such as 7.20.1 kept as a level of their own), a numbered list inside one section (1. 2. 3. …),
    and flowcharts, including ones that run over pages.
  - Something only counts as a procedure when it reads as instructions (its title, or
    "Verify …", "Press …", "Install …" lines). Manuals, specifications, spreadsheets, code and
    web pages stay plain sections and search exactly as before.
  - It is built from the stored chunks alone, so `rag spots` (or **Details → Build structure**)
    gives a 0.4.0 knowledge base the same structure. Nothing is read or embedded again.
  - It is only used while it matches its `rag.db`. A missing, out-of-date or damaged spots file
    is ignored, and search then works exactly as in 0.4.0.
- **A hit inside a procedure brings the procedure**, as much of it as fits in 1,500 tokens.
  - A short procedure comes back whole, with a heading per step.
  - In a longer one, the matched step and one step on each side.
  - A step too long for that (a test cycle with fifteen sub-steps) comes back as the sub-steps
    around the match, and a long step without sub-steps as the chunks around the match. Either way
    the result still says where it sits: "step 7.20 of 40, sub-steps 7.20.6-7.20.8".
  - The source line names the document, its revision and the steps:
    `pump.pdf · DOC-12 rev A · p.14 · … · 8.0 Filter Replacement (whole, 4 steps)`.
  - The first result from a long procedure carries an outline: the steps around it, the
    included ones marked, so the reader knows what comes before and after.
  - References in the passage are listed under it:
    `Related: section 8.4 Restarting after an alarm; FX-100 (Fixtures/FX-100.pdf)`.
  - One long procedure doesn't take over the results: at most three come from one procedure
    while other documents still have something to give (more fill places nothing else took),
    and a hit in the step right next to one already returned widens that result instead of
    coming back as a separate fragment.
  - Settings: `[search] procedures`, `procedure_tokens`, `procedure_window`, `procedure_hits`.
- **Reading on through a long procedure.** A result that holds only part of a procedure ends
  with the call that continues it: `Read on: get_procedure_steps(procedure=12, from="7.35")`.
  Each page holds as many steps as fit (a step too long for a page is paged by its chunks) and
  ends with the call for the next one, or "(the procedure ends here)". Complete results never
  show the line, so an agent only meets it when there is more to read.
  - In the app: **Show the whole procedure** beside a partial result in Search.
  - On the command line: `rag procedure KB 12 --from 7.35`.
  - In the retrieval server: `ShammyRetriever.ProcedureSteps(...)` and `RetrievalHit.More`; the
    server guide has the MCP tool and a description that tells the agent when to call it.
- **Search one document.** Filter by document number or part of the file name: the field beside
  the search box in the app, `rag search --doc DOC-12`, and `documents` in the engine request
  (`RetrievalOptions.Documents` in C#).
- **Numbered headings nest by their numbers.** A PDF that gives "8.0 Filter Replacement" the
  wrong heading level no longer files 8.1–8.4 under 7.0. This applies to documents read from now
  on; the spots file uses the numbers anyway, so older knowledge bases get the right procedures
  too.

## Embedded text names the document

- **New knowledge bases add a line naming the document to every chunk before it is embedded**:
  its title, document number and revision, for example "Pump assembly (WI-0300 rev C)". A
  question that names a document or a piece of equipment from its title reaches that document's
  chunks, and similar procedures in different documents are told apart better.
- **Existing knowledge bases are not changed.** Vectors made with and without the line don't mix
  well, so each knowledge base records which form it was built with and keeps it. A 0.4.0
  knowledge base keeps building and searching exactly as before. To switch one, build a new
  knowledge base next to it and compare the two on your own questions before retiring the old
  one. The Details tab shows which form a knowledge base uses ("Embedded text").

## Builds you can follow

- The Build tab shows the time so far and an estimate of the time left, and for the file being
  read what is happening to it with its own bar: "Reading page 12 of 40", "Describing pictures
  (3 so far)", "Split into 84 chunks", "Embedding 40 of 84 chunks". Reused vectors count as done
  from the start, so an update that changes little moves quickly.
- The activity list gives each file's chunks and time; unchanged files are counted, not listed.
- The Documents tab shows the file being built with its stage and live counts ("40 of 84 chunks
  embedded"). The knowledge base still receives a document in one piece when it is finished, so
  a search never sees half a document.
- The Build tab follows a running build of its knowledge base wherever it was started.
- `rag build` on a terminal keeps one status line that updates in place (bar, files, the current
  file and stage, time left); piped output is unchanged.

## Updates

- **The app updates itself.** A few seconds after it starts it checks the project's latest
  GitHub release; when there is a newer version a bar at the top shows it and what's new.
  **Update and restart** downloads it, checks its signature against the key built into the app,
  stops the engine and the model servers, installs and restarts. Nothing installs without being
  asked, and it waits while a build, merge or export is running.
- Settings → Updates turns the start-up check off or runs it by hand.
- `rag update --check` says whether a newer release exists.
- The Windows installers and the `.AppImage` update this way; a `.deb` install is updated with a
  new `.deb`.

## Reading documents

- **Text read from pictures is checked against the picture's description.** When the picture
  model describes a picture, only the OCR lines its description confirms are kept as "Text in
  figure". OCR invents words on glare, engraved labels and small screen text ("Hot Surfcae",
  "MotorOverlaod"); the vision model reads the whole picture and copies its labels. Without
  descriptions, unsure OCR fragments are now left out of figure text (tables still re-read their
  cells). This applies to documents read from now on.

## Retrieval server

- `ShammyRetriever` reads the spots file of a pack exported by 0.4.1. `RetrievalHit` gains
  `Document`, `Revision`, `Procedure`, `Outline`, `Related` and `More`; `RetrievalOptions` gains
  `Procedures`, `ProcedureTokens`, `ProcedureWindow`, `ProcedureHits` and `Documents`;
  `ShammyRetriever.Procedures` says whether a current spots file was found. Older packs give
  exactly the results they gave before.
- **The wrapper's assembly is now `Shammy.Net.dll`.** It was `Shammy.dll`, the same file name on
  Windows as the native `shammy.dll`, so a server that referenced the wrapper project ended up
  with only one of the two in its output folder. The release zip (`shammy-native-Windows.zip`)
  now also carries the wrapper's two source files and a README explaining which DLL is which:
  `shammy.dll` is native and is copied next to the executable, not added with *Add Reference*.
- New C function `shammy_rag_procedure` (see `shammy.h`).

## Other changes

- The project is domain-neutral: the built-in crawler presets for one vendor's products are
  replaced by an `example` template, and the docs, tests and samples use a fictional pump maker.
- New app icon.

## Compatibility

- 0.4.0 knowledge bases and packs open, build and search unchanged. `rag spots` (or Details →
  Build structure) adds procedures without reading or embedding anything.
- Packs exported by 0.4.1 open in 0.4.0, which ignores the spots file.
- The engine's JSON request and response only gain fields.
- The two vendor-specific crawler presets are gone; copy the `example` preset
  (`rag-crawl preset example`) and put in your own topic.
