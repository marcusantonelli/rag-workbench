# RAG Workbench v0.4.0

The largest release so far: a vector store of our own (Shammy), one search engine shared by the
Workbench and the retrieval server, an optional reranker and picture model the app downloads and
runs for you, and a reader that handles flowcharts, procedure tables, pictures of tables and forms.

## Reading documents

- **Flowcharts in PDFs are rebuilt, not read as jumbled text.** A flowchart drawn as shapes
  (exports from Visio, PowerPoint, draw.io, Word) becomes numbered steps, each with where it
  leads, branch labels such as Yes and No, and swimlane names, plus a picture of the drawing.
  - Arrowheads drawn filled or as two strokes, connectors drawn in pieces, branches, two-way
    arrows and plain links are all understood.
  - A flowchart that runs over several pages is linked by its off-page connectors ("continues on
    page 4"), and boxes of notes beside the flow are attached to the step they sit next to.
  - Tables drawn with boxes, charts and unconnected text boxes are left alone.
  - Setting: `[pdf] diagrams`.
- **Work instructions laid out as one long table are read as a document.** A procedure set out
  as STEP | PROCEDURE | DESCRIPTION | VISUAL over many pages becomes a heading per step, its
  bullets in order, and each photograph or screenshot labelled with the step it illustrates.
  Steps that carry on across rows and pages stay together, sub-steps that start part-way down a
  cell get their own heading, and small tables inside cells stay tables.
- **Pictures of tables and spreadsheets become real tables**, in PDFs and Word files. Rows and
  columns are rebuilt from where each cell sits, Excel's own row numbers and column letters are
  dropped, and cells the OCR skipped (a lone "0") are read a second time. The table keeps its
  picture so values can be checked, and large ones can be queried with SQL. Tables on scanned
  pages are read the same way. Setting: `[figures] table_ocr`.
- **Forms.**
  - Values typed into fillable PDF fields are read, including fields inside table cells. They
    aren't part of the page text, so they used to be lost. Checkboxes and radio buttons read as
    ☒ ☐ ◉ ○. Setting: `[pdf] form_fields`.
  - Forms laid out as label/value grids become "Label: value" lines instead of a table whose
    first row was taken for column names.
  - Word: text in content controls (where Word forms keep their fields), content-control, legacy
    and symbol checkboxes, and tracked changes (insertions kept, deletions dropped).
  - Wingdings boxes and ticks in PDFs and Word files read as ☐ ☑ ☒ ✓ ✗.
- **Large tables are chunked in full** (up to 1,000 rows, in row groups under the column names)
  as well as stored for SQL, so a question about one row finds it. Setting:
  `[chunking] table_chunk_max_rows`.
- **Picture descriptions (optional).** A small vision model describes each photo and screenshot
  during a build: the equipment, controls, labels, screen titles and settings it can read.
  - Turn it on in **Settings → Picture descriptions**. Choose Qwen3-VL 4B (about 3 GB,
    recommended) or Qwen3-VL 2B (about 1.5 GB); the app downloads it and runs it beside the
    embedding model, on the GPU when there is room and otherwise on the CPU. Switch models or
    turn it off at any time.
  - The model is told which procedure step a picture illustrates. Redaction boxes and blank
    frames are skipped, and flowcharts keep their exact rebuilt steps.
  - Documents with pictures are read again the next time you build; documents without pictures
    are left alone. If the model stops answering mid-build, the build finishes and the next one
    tries again.
  - Command line: point `RAG_DESCRIBE_URL` or `[figures] describe_url` at any OpenAI-compatible
    endpoint (see `docs/cli.md`).

## Search

- **Reranker (optional).** A small reranker model reads the question with each of the best 20
  results and reorders them before the top ones are kept.
  - Turn it on in **Settings → Reranker**: download Qwen3-Reranker 0.6B (about 640 MB) or use a
    reranker `.gguf` of your own (for example a 4B or 8B Qwen3-Reranker). The app runs it beside
    the embedding model; switch or turn it off at any time.
  - While it's on, every search in the app is reranked; the Search tab's switch turns it off for
    one search.
  - If the reranker can't be reached, the search still answers in the usual order and says it
    wasn't reranked.
  - Command line: `rag search --rerank`, `[rerank] enabled = true` in `config.toml`, and
    `--rerank-url` or `RAG_RERANK_URL` for the address of any `/v1/rerank` server.
- **One search implementation everywhere.** Everything after the query is embedded (vector and
  keyword search, rank fusion, duplicate removal, reranking, neighbour expansion, citations, the
  agent's Markdown form) runs in one shared engine. The Workbench calls it from Python and the
  retrieval server from C# (`ShammyRetriever`), so the agent gets exactly what the Search tab
  shows, for sqlite-vec and Shammy knowledge bases alike.

## Shammy, our own vector store

- A workspace can keep its vectors in a single `vectors.shammy` file instead of inside `rag.db`.
  - About 12.8 KB per chunk at 4096 dimensions, against 16.4 KB in sqlite-vec.
  - A search scans a 1-bit sketch of every chunk, reranks on 1-bit and 8-bit codes, then
    rescores the best 50 exactly: 1 to 2 ms for 50,000 chunks at 4096 dimensions on one thread.
  - AVX2 or AVX-512 when the CPU has them, and as many threads as you allow (default: two fewer
    than the machine's cores). Results are identical on every CPU and thread count.
  - Every section of the file has a checksum, and an interrupted write never damages what was
    already saved.
- **Choosing it:** New knowledge base offers the vector store, and **Details** shows which one a
  knowledge base uses, with a button to move the vectors either way. Command line:
  `rag init WS --vectors shammy`, `rag convert WS` (and `--to sqlite-vec`). Nothing is embedded
  again.
- **`rag compact WS`** rewrites `vectors.shammy` without deleted rows; builds do it on their own
  when a quarter of the rows are deleted.
- **`rag export --slim`** leaves the float16 vector copies out of a Shammy pack: about 4.6 KB of
  vectors per chunk instead of 12.8 KB. A slim pack skips the exact rescore and can't be merged.
- **Import from other databases:** `shammy-convert sqlite` (sqlite-vec and ordinary SQLite
  tables) and `shammy-convert pgvector` (a PostgreSQL pgvector column).
- **For other programs:** a Python module (`shammy`), a C interface and a C# wrapper. The native
  library (`shammy.dll`, `libshammy.so`) and `shammy.h` are attached to the release as
  `shammy-native-<OS>.zip`; `shammy/dotnet/README.md` shows the one-call change the .NET
  retrieval server needs. C, C# and Python return identical results.

## App

- **Details** and **Documents** update while a build runs: counts and size refresh every few
  seconds, and Details says the numbers are still changing. Documents has a Refresh button.

## Changed

- **Docling is gone.** The built-in PDF reader handles everything above, and Docling bypassed it.
  A `pdf.backend` setting in older `config.toml` files is ignored.
- A table's column-header row that repeats at the top of each page is no longer removed as a page
  header, and a header row drawn above the first ruling line is kept as the column names.
- A picture or table wider than the text around it stays at its place on the page; it used to be
  moved to the end of the page, which also lost its caption.
- Pictures inside a section no longer cut its text into small chunks.
- The reranker's default address is port 8082 (8081 is the embedding model's); the picture model
  uses 8083.
- `rag verify` on a Shammy workspace also checks every checksum in `vectors.shammy`; `rag status`
  and `rag verify` show which vector store a workspace uses.
- After a crash mid-build on Shammy, the next build drops vectors that have no chunk and reads
  again any document whose vectors didn't reach the disk.
- **Your documents are read again on the first build after upgrading** (PDFs and Word files),
  to pick up the reader changes. Text that didn't change keeps its vectors.

## Compatibility

- sqlite-vec stays the default; existing workspaces and `ragpack/1` packs are unchanged.
- A pack exported from a Shammy workspace is format **`ragpack/2`**. This version reads both. The
  retrieval server reads `ragpack/2` once it uses the C# wrapper; until then, keep workspaces
  that feed it on sqlite-vec.
- Shammy needs a vector size that is a power of two (1024, 2048, 4096).
- Moving from Shammy back to sqlite-vec writes Shammy's float16 copies of the vectors, which
  differ from the originals only past the fourth significant digit.

## Known limits

- Data tables aligned only by spaces (no ruling lines) are read as lines of text.
- Reading a scanned page or picture that holds a large table takes about three times as long as
  plain OCR, because cells the first pass skipped are read again one by one.
- Planned for 0.4.1 and 0.4.2: page headers and footers (keeping document numbers and revisions,
  removing them from scanned pages), text boxes in Word files, and forms on scanned pages.
