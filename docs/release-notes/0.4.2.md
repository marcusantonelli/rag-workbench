# RAG Workbench v0.4.2

Search answers with the surrounding section in every document with headings, not only in
procedures. PDF and Word documents with flowcharts, side panels and titled tables are read by
the same general layout rules rather than one-off fixes. Rebuilding from scratch works while the knowledge base is open
elsewhere, the time-left estimate no longer runs away, and a build can be stopped in the middle
of a file.

Knowledge bases built with 0.4.0 and 0.4.1 keep working. The next build (or **Details → Build
structure**) adds sections in seconds, without reading or embedding anything again.

## Sections: document-wide context for every document

- **A hit in a manual, report, specification or web page comes back with its section.** In 0.4.1
  only procedures did this; every other hit came back as the chunk and its neighbours. Now the
  spots file also records the sections of every document with headings (PDF, Word, Markdown,
  HTML, text, slides).
  - A manual with long chapters gets a section per chapter, its sub-headings as parts.
  - A document of many short sections (most reports, specifications and web pages) is one section
    with its headings as parts.
- **What a hit brings**, as much as fits in 1,200 tokens:
  - The whole section, when it is that short. A table that matched comes back with the text and
    heading above it.
  - Otherwise, the part that matched and the parts on each side, or the chunks around the match
    when one part is too long.
  - The source line says what was included: `Garden pump handbook (Error codes, of 12 parts)`.
  - The first result from a long section carries an outline of it, the included parts marked.
  - The result ends with the same `Read on: get_procedure_steps(...)` call procedures use. Its
    `from` is a part's title.
- "See section 4.2" references now link in any document with numbered headings, not only inside
  procedures.
- The same limits as procedures apply. At most three results come from one section while other
  documents have something to give, and a hit in the part next to one already returned widens
  that result.
- **Spreadsheets, CSV files, code and SQL have no sections and search exactly as before.**
- Settings: `[search] sections` (on) and `section_tokens` (1200). With sections off, hits come
  back with their neighbouring chunks, as in 0.4.1.
- In the app, Search shows "Show the whole section" beside a partial result. Details counts
  sections and offers to rebuild a structure made by 0.4.1.

## Reading PDF and Word documents

These are general rules for shapes that appear in many documents, not fixes for one file. They
apply to documents read from now on: new and changed files, or everything after **Rebuild
everything from scratch**. Files already in a knowledge base aren't read again on their own,
because that would describe all their pictures again.

### PDF

- **Flowcharts drawn with block arrows** (wide filled arrows instead of lines with arrowheads)
  are read with their connections. White masking boxes no longer count as shapes.
- **Boxed panels are text, not tables.** A ruled box with one column, or one whose rows never
  have two filled cells (a checklist panel, a side note, a cover block), is read as text in
  reading order. It used to be a one-column table, out of order.
  - A box that carries a table on from the previous page is still read as that table, even when
    its last rows fill one column only.
- **Tables:**
  - A first row holding only a title ("Troubleshooting") becomes the table's caption and starts
    a section of that name.
  - Empty numbered rows ("4.", "5." with nothing after them) are dropped.
  - A column that a stray rule split off its neighbour is joined back to it.
  - A table split into parts by one-cell rows (sub-headings inside the grid) has each part
    tidied on its own, so one part's empty columns don't disturb another's.
- A line that starts in lower case is never taken for a heading, however large its type. It is
  a sentence carrying on.
- A heading with nothing under it before the next heading is also kept as text, so it can be
  found by search. This applies to every format except code, and not to the document's own
  title.

### Word (.docx, and .doc through LibreOffice)

- **Tables follow the same rules as in PDFs**, from one shared set:
  - A first row merged across the table is its title: the caption, and a heading for the section.
  - A row merged across the table further down names the part after it.
  - Empty numbered rows are dropped.
  - A table of one column, or one whose rows never have two filled cells, is text, one line per
    cell. It used to be one line joined with " / ".
  - Two-row headers (a merged group over its columns) still become "Group / Column" names.
- **Text boxes and shapes are read.** Their text used to be skipped entirely. It now follows the
  paragraph the shape is anchored to, in reading order. Word's older copy of each shape (kept for
  old readers) is never read as well, and documents from before Word 2010 give their text-box text
  too.
- **Flowcharts drawn with Word's shapes** become numbered steps with where each leads, the same
  text as a flowchart rebuilt from a PDF. This works for shapes in a group or drawing canvas, and
  for separate floating shapes in the same section. Connectors count whether they are glued to the
  shapes or just end on them. Short loose labels ("Yes", "No") go on the connector beside them. A
  shape no connector touches (a note beside the chart) stays text.

## Builds

- **Rebuild everything from scratch works while the knowledge base is open.** On Windows the
  build could stop with "rag.db is in use" when a search, the Documents tab, the retrieval server
  or a virus scanner had the file open. A database that can't be deleted is now emptied in place,
  and a vector file that can't be deleted is cleared. If the open vector file was made for a
  different vector size, the build says to close the other program first.
- **Stop… → Now.** The **Stop…** button offers **After the current file** (as before) and **Now**.
  Each choice says what it does:
  - Now stops in the middle of the current file. Nothing read from it so far is kept, and the next
    build reads it again.
  - Files finished before it stay.
  - If the file was an update, its previous version was already replaced when the build started
    it, so it is missing until the next build.
- **Two time-left figures, and neither creeps up.** While pictures were being described, the old
  estimate ignored how far the file had got, so on a long PDF it climbed every second (into
  hundreds of hours).
  - **This file:** the pages left at the pace of the pages read so far, plus embedding its likely
    chunks at the pace measured on earlier files; while embedding, the chunks left at this file's
    pace.
  - **In all:** shown only once there is enough to go on (30 seconds of work, and three files read
    or a tenth of the work measured). Until then the Build tab says it is working it out.
  - Both are worked out again only when the build moves, count down in between, and ease toward
    each new figure instead of jumping. `rag build` on a terminal eases its estimate the same way.

## Updates: pre-releases

- **Settings → Updates → Also offer pre-releases** (off by default). With it on, the app is also
  offered test versions published before the next normal release. With it off, nothing changes.
- While a pre-release is installed, a small **Pre-release** mark sits beside the app's name, in
  Settings → About and on the update bar. Every other 0.x version shows **Alpha** there instead:
  the app is in alpha until 1.0 (see "Versions" in the README and the new `CHANGELOG.md`).
- Turning the setting off doesn't go back to an older version. The next normal release newer than
  the installed one is offered as usual.
- `rag update --check --pre` counts pre-releases too.
- For maintainers: tag a pre-release `v0.4.3-1`, `v0.4.3-2`, and so on (the Windows `.msi` builder
  only takes numbers after the hyphen). The release workflow marks such a tag as a pre-release.
  Publishing any release updates the pre-release feed. See the desktop README.

## Retrieval server and engine

- Results gain sections: `RetrievalHit.Procedure.Kind` is `"section"` for them. New options:
  `RetrievalOptions.Sections` and `SectionTokens`; JSON `sections` and `section_tokens`.
- `ProcedureSteps` and `shammy_rag_procedure` read on through sections the same way. The guide's
  tool description for `get_procedure_steps` now covers sections.
- `ShammyRetriever.Procedures` still counts procedures only.

## Compatibility

- 0.4.0 and 0.4.1 knowledge bases and packs open, build and search unchanged.
  - A spots file made by 0.4.1 is still used for its procedures.
  - The next build, `rag spots` or Details → Build structure adds sections.
- The spots file keeps its format, so a 0.4.1 app or retrieval server still reads a pack exported
  by 0.4.2. It takes sections for procedures: whole up to 1,500 tokens, with "steps" in the
  wording. Update `shammy.dll` with the app to get the 0.4.2 behaviour.
- The engine's JSON request and response only gain fields.
- **Search results change for documents with headings:** a hit now carries its section (or the
  parts around it) instead of its neighbouring chunks. To keep the 0.4.1 behaviour, set
  `[search] sections = false`.
